FD Table Core 학습 노트

Pintos Project 2의 B5를 구현하기 전에 fd table의 역할과 설계 선택지를 이해하기 위한 문서입니다. 이 문서는 정답 코드가 아니라, 스스로 구현 결정을 내리기 위한 개념 지도와 질문 목록입니다.

한 줄 개념

fd table은 프로세스가 가진 열린 파일들을 fd 숫자로 다시 찾기 위한 per-process 자료구조입니다. fd는 파일 자체가 아니라 현재 프로세스 안에서만 의미 있는 핸들입니다.

공부 목표: B5는 open, filesize, read, write, close, exit cleanup이 공통으로 의존하는 기반입니다. 이 문서를 읽은 뒤에는 "fd 숫자가 실제 파일 작업으로 이어지는 경로"를 말로 설명할 수 있어야 합니다.

fd는 파일이 아니다

유저 프로그램이 syscall에 넘기는 것은 파일 객체가 아니라 작은 정수인 fd입니다. 커널은 그 정수를 현재 프로세스의 fd table에서 해석해야 합니다.

1. 유저 요청유저 프로그램이 fd 숫자를 syscall 인자로 넘김
2. 현재 프로세스커널은 지금 실행 중인 프로세스의 table만 봄
3. fd 해석fd 숫자가 열린 파일 정보와 연결되는지 확인
4. 파일 작업유효할 때만 실제 file API로 넘어감
생각해보기: 같은 fd 숫자라도 프로세스가 다르면 왜 다른 파일을 가리킬 수 있을까요?

B5-A. 구조 설계

fd entry는 fd 숫자와 열린 파일 사이의 연결을 표현합니다. open file object는 "열린 파일 상태"를 fd entry와 분리해서 생각하기 위한 개념입니다.

fd entry를 볼 때

  • fd 숫자를 기억해야 하는가?
  • 실제 파일을 직접 가리킬 것인가?
  • table 안에서 entry를 찾기 위한 연결 정보가 필요한가?
  • entry의 생명주기는 언제 시작하고 끝나는가?

open file object를 볼 때

  • 열린 파일의 실제 소유권을 어디에 둘 것인가?
  • 여러 fd가 같은 열린 파일을 공유할 수 있는가?
  • 마지막 참조가 사라졌다는 것을 어떻게 알 수 있는가?
  • file position 공유가 필요한 상황은 무엇인가?
핵심 구분: fd entry는 "번호와 연결"에 가깝고, open file object는 "열린 파일 상태와 소유권"에 가깝습니다.

B5-B. stdin/stdout

fd 0과 1은 일반 파일이 아니라 예약된 표준 입출력입니다. 일반 파일 fd와 같은 table lookup 흐름에 넣을지, syscall에서 특수 처리할지는 설계 선택입니다.

fd 의미 read 관점 write 관점
0 stdin 입력 장치에서 읽는 특수 fd 일반적으로 잘못된 방향
1 stdout 일반적으로 잘못된 방향 콘솔 출력으로 이어지는 특수 fd
2+ 일반 파일 fd table lookup 필요 fd table lookup 필요
  • open()이 fd 0이나 1을 반환하면 왜 곤란한지 설명해봅니다.
  • read(1)과 write(0)의 실패 정책을 일관되게 정해야 합니다.

B5-C. fd 할당 정책

fd allocation은 새로 열린 파일에 어떤 fd 숫자를 줄지 정하는 규칙입니다. 쉬운 정책과 더 일반적인 정책 사이의 장단점을 이해해야 합니다.

정책 아이디어 좋은 점 고민할 점
단순 증가 다음 후보 fd를 계속 증가시킴 이해와 구현이 쉽다 닫힌 fd를 바로 재사용하지 않는다
빈 번호 재사용 사용 중이지 않은 작은 fd를 찾음 fd 숫자가 작게 유지된다 중복 확인과 탐색 규칙이 필요하다
스스로 정할 것: 어떤 정책을 고르든 fd 0과 1은 예약되어 있고, 일반 파일 fd는 2 이상이어야 합니다.

B5-D. fd lookup

lookup은 fd 숫자가 현재 프로세스의 열린 파일과 연결되는지 확인하는 공통 관문입니다. filesize, read, write, close가 같은 기준을 공유해야 합니다.

  • fd가 일반 파일 범위인가?
  • 현재 프로세스의 fd table에 실제로 존재하는가?
  • 존재하지 않는다면 syscall은 어떤 값이나 상태로 실패하는가?
  • lookup 실패가 실제 file API 호출로 흘러가지 않도록 어디에서 막을 것인가?
위험 신호: invalid fd가 file API의 null 인자로 이어지면 커널 panic 가능성이 큽니다.

B5-E. close/remove

fd를 닫는 일은 table에서 번호를 제거하는 일과 열린 파일 참조를 정리하는 일을 모두 포함합니다. 둘 중 하나만 하면 fd table 상태와 파일 객체 상태가 어긋납니다.

table 관점

  • entry가 더 이상 lookup되지 않아야 합니다.
  • 같은 fd를 다시 닫아도 커널이 죽지 않아야 합니다.
  • entry 메모리 생명주기를 정해야 합니다.

file 관점

  • 파일 참조를 언제 내려놓을지 정해야 합니다.
  • shared 구조라면 마지막 참조인지 확인해야 합니다.
  • file system lock 정책과 맞아야 합니다.

B5-F. exit cleanup

유저 프로그램이 열린 파일을 모두 닫고 종료한다고 기대하면 안 됩니다. 프로세스 종료 경로에서 남아 있는 fd 전체를 정리해야 합니다.

  • 진짜 프로세스 종료 경로가 어디인지 확인합니다.
  • 주소 공간 정리와 fd 정리의 순서를 생각합니다.
  • table을 순회하면서 entry를 제거할 때 안전한 순회 방식이 필요한지 봅니다.
  • exec 중 cleanup과 exit cleanup을 구분해야 하는지 확인합니다.
  • 실행 파일 write deny를 구현했다면 그 파일의 close 흐름도 같이 봅니다.

B5-G. shared/ref 구조

dup2를 생각하면 fd table 설계에서 소유권 문제가 드러납니다. fd 두 개가 같은 열린 파일을 가리킬 수 있다면, fd entry가 직접 파일을 소유하는 모델은 조심해야 합니다.

fd entryfd 숫자와 열린 파일 상태 사이의 연결
open file실제 열린 파일 상태와 file position
ref count그 상태를 가리키는 fd entry 수
close 조건마지막 참조가 사라졌을 때 실제 파일 close
생각해보기: fd A와 fd B가 같은 열린 파일을 공유할 때, fd A만 닫으면 실제 파일을 닫아도 될까요?

read/write와의 연결

read/write 구현은 B5 위에 올라갑니다. fd table은 "어떤 파일인가"를 해결하고, buffer validation은 "유저 메모리에 접근해도 되는가"를 해결합니다.

관심사 담당하는 질문 관련 테스트
fd table fd가 현재 프로세스의 열린 파일인가? bad fd, normal read/write
stdin/stdout 예약 fd를 올바른 방향으로 쓰고 있는가? read-stdout, write-stdin
buffer validation 유저가 넘긴 메모리 범위가 안전한가? bad-ptr, boundary
return value syscall 결과가 유저에게 정확히 돌아가는가? zero, normal 계열

테스트 그룹 B5와의 관계 확인할 개념

자기 점검

fd는 파일이 아니다 per-process stdin/stdout allocation lookup close/remove exit cleanup shared/ref buffer validation

  • fd table이 왜 프로세스별이어야 하는지 설명할 수 있다.
  • fd 0, fd 1, fd 2 이상의 차이를 설명할 수 있다.
  • fd allocation 정책 하나를 고르고 장단점을 말할 수 있다.
  • lookup 실패가 왜 커널 panic으로 이어지면 안 되는지 설명할 수 있다.
  • close가 table remove와 file 참조 해제를 모두 포함한다는 것을 이해한다.
  • exit cleanup이 필요한 이유를 설명할 수 있다.
  • shared/ref 구조가 왜 dup2와 관련 있는지 설명할 수 있다.
  • fd table 문제와 buffer validation 문제를 구분할 수 있다.
