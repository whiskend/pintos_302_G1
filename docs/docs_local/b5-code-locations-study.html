B5 수정 지점 3, 4, 5 코드 읽기

syscall.c, process.c, syscall.h가 FD Table Core에서 어떤 책임을 갖는지 이해하기 위한 학습 문서입니다. 이 문서는 구현 방법이나 정답 코드를 제공하지 않고, 현재 코드의 역할과 읽는 관점만 설명합니다.

문서 범위

이전에 짚은 수정 위치 중 3번, 4번, 5번만 다룹니다. 세 파일은 서로 다른 층위에 있습니다. syscall.c는 syscall 요청이 들어오는 입구, process.c는 프로세스 종료와 자원 정리의 자리, syscall.h는 다른 파일에서 syscall 관련 함수를 볼 수 있게 하는 경계입니다.

주의: 여기서는 "어디에 어떤 코드가 들어간다"를 완성 형태로 쓰지 않습니다. 대신 각 파일을 읽을 때 어떤 책임을 찾아야 하는지 설명합니다.

B5에서의 최종 목표

B5의 목표는 read나 write 테스트를 바로 통과시키는 것이 아닙니다. 목표는 "현재 프로세스가 가진 열린 파일 목록을 fd 숫자로 관리할 수 있는 내부 기반"을 만드는 것입니다.

구분 B5에서 해야 함 B5만으로는 아직 아님
fd 저장 열린 파일을 현재 프로세스의 fd table에 넣을 수 있어야 한다. 모든 file syscall 테스트가 통과하는 것까지는 아니다.
fd 찾기 fd 숫자로 현재 프로세스의 열린 파일 정보를 다시 찾을 수 있어야 한다. read/write의 buffer 검증 전체가 완성된 상태는 아닐 수 있다.
fd 닫기 fd 하나를 table에서 제거하고 파일 참조를 정리할 수 있어야 한다. close syscall 테스트가 바로 통과한다는 뜻은 아니다. syscall 연결도 필요하다.
종료 정리 프로세스 종료 시 남아 있는 fd 전체를 정리할 수 있어야 한다. wait/exit 출력, exit status 전달까지 모두 해결했다는 뜻은 아니다.
확장 대비 dup2를 생각했을 때 shared/ref 구조가 필요한지 판단해야 한다. dup2 syscall 자체를 완성해야 한다는 뜻은 아니다.
한 문장으로: B5가 끝났다는 말은 "fd table이라는 내부 서비스가 준비되었다"는 뜻입니다. 아직 유저 프로그램 입장에서는 syscall 연결이 덜 되어 있으면 눈에 보이는 PASS가 없을 수 있습니다.

세 파일 한눈에 보기

번호 파일 현재 코드에서 보이는 것 B5에서 보는 관점
3 pintos/userprog/syscall.c syscall_init(), syscall_handler(), 일부 syscall 분기 fd를 인자로 받는 syscall들이 fd table을 사용하게 되는 입구
4 pintos/userprog/process.c process_exit(), process_cleanup() 프로세스가 죽을 때 남은 fd 자원을 정리해야 하는 자리

결론: 진짜 작업 목록

이 세 파일에서 해야 하는 일은 "fd table 내부 기능을 만들고, 그 기능이 필요한 파일 경계를 연결하는 것"입니다. 아래 목록은 B5를 끝냈다고 말하기 위해 확인해야 하는 작업입니다.

파일 해야 할 일 완료 기준
syscall.c fd entry를 만들고 없애는 내부 책임을 둔다. fd 하나가 어떤 파일 참조를 뜻하는지 커널 내부에서 표현할 수 있다.
syscall.c 새 fd 번호를 고르는 책임을 둔다. 일반 파일 fd가 2 이상에서 시작하고, 새 파일마다 충돌 없이 번호를 받을 수 있다.
syscall.c 열린 파일을 현재 프로세스의 fd table에 등록하는 책임을 둔다. 파일이 열렸을 때 fd table에 entry가 생기고, 유저에게 돌려줄 fd 번호가 정해진다.
syscall.c fd 숫자로 fd table을 조회하는 책임을 둔다. 없는 fd, stdin/stdout, 일반 파일 fd를 구분할 수 있다.
syscall.c fd 하나를 닫고 제거하는 책임을 둔다. 닫힌 fd가 다시 lookup되지 않고, 파일 참조도 정리된다.
syscall.c 현재 프로세스의 fd를 전부 닫는 cleanup 책임을 둔다. 프로세스 종료 시 남은 fd를 한 번에 정리할 수 있다.
process.c 프로세스 종료 흐름에서 fd 전체 cleanup이 호출되도록 연결한다. process_cleanup()로 주소 공간을 없애기 전에 파일 자원 정리 흐름을 생각했다.
syscall.h process.c에서 호출해야 하는 fd cleanup 함수가 있다면 선언을 공개한다. 외부에서 필요한 함수만 보이고, fd lookup 같은 내부 helper는 숨겨져 있다.
중요: "해야 할 일"은 구현 순서와 책임을 뜻합니다. 이 문서는 어떤 문장을 그대로 코드로 옮기라는 답안지가 아닙니다.

작업 순서

헷갈릴 때는 아래 순서대로 생각하면 됩니다. 순서는 "구현 정답"이 아니라 의존 관계를 따라간 공부 순서입니다.

  1. 먼저 fd table이 저장될 장소가 이미 준비되어 있는지 확인합니다. 이 부분은 1번, 2번 수정 위치인 thread.h와 thread.c에 가깝습니다.
  2. syscall.c에서 fd entry가 무엇을 담아야 하는지 정합니다.
  3. syscall.c에서 새 fd 번호를 어떤 정책으로 줄지 정합니다.
  4. syscall.c에서 열린 파일을 fd table에 넣는 내부 흐름을 만듭니다.
  5. syscall.c에서 fd 숫자로 fd table을 찾는 내부 흐름을 만듭니다.
  6. syscall.c에서 fd 하나를 닫는 내부 흐름을 만듭니다.
  7. syscall.c에서 현재 프로세스의 fd 전체를 닫는 내부 흐름을 만듭니다.
  8. process.c에서 프로세스 종료 흐름과 fd 전체 cleanup을 연결합니다.
  9. syscall.h에는 process.c가 알아야 하는 함수만 공개합니다.
  10. 마지막으로 open, filesize, read, write, close가 나중에 이 fd table 기능을 어떻게 사용할지 말로 설명해봅니다.
B5 완료 감각: "파일을 열면 fd table에 들어간다. fd 숫자로 다시 찾을 수 있다. fd 하나를 닫을 수 있다. 프로세스가 죽으면 남은 fd를 다 닫을 수 있다." 이 네 문장을 코드 흐름으로 추적할 수 있으면 B5의 뼈대가 잡힌 것입니다.

아직 하지 않는 일

B5를 하다 보면 file syscall 전체를 한 번에 끝내고 싶어지지만, 지금 작업의 초점은 fd table core입니다. 다음 항목들은 B5와 연결되지만, B5만의 완료 기준은 아닙니다.

  • read/write의 모든 bad pointer, boundary buffer 처리를 완성하는 것
  • create, remove, seek, tell까지 전부 완성하는 것
  • dup2 syscall 자체를 끝까지 구현하는 것
  • 모든 userprog file syscall 테스트를 통과시키는 것
그래도 생각은 해야 함: B5-G 때문에 dup2의 shared/ref 구조는 미리 고려합니다. 다만 syscall 전체를 완성하는 작업과, fd table이 그 상황을 버틸 수 있게 설계하는 작업은 다릅니다.

3. syscall.c 읽기

syscall.c는 유저 프로그램이 syscall을 호출했을 때 커널이 처음으로 해석하는 파일입니다. B5 입장에서는 "fd 숫자를 받은 뒤 fd table 쪽 사고로 넘어가는 문"이라고 보면 됩니다.

include 영역

파일 위쪽의 include들은 이 파일이 어떤 커널 기능을 알고 있는지 보여줍니다. 현재는 syscall 번호, interrupt frame, thread 정보, 저수준 syscall 진입 설정에 필요한 헤더들이 포함되어 있습니다. B5를 공부할 때는 "fd table을 다루려면 어떤 자료구조와 파일 API 지식이 필요할까?"를 생각하면 됩니다.

이 파일에서 해야 할 일

  • fd table 내부에서 쓸 helper들을 이 파일 안에 둘지, 별도 파일로 뺄지 결정합니다. 현재 프로젝트 규모에서는 syscall.c 안에 두는 선택이 단순합니다.
  • fd entry 생성과 제거의 책임을 정합니다.
  • fd 번호 할당 정책을 정합니다. 단순 증가인지, 빈 번호 재사용인지 먼저 골라야 합니다.
  • 열린 파일을 현재 프로세스 fd table에 등록하는 흐름을 만듭니다.
  • fd 숫자로 현재 프로세스 fd table을 조회하는 흐름을 만듭니다.
  • fd 하나를 닫는 흐름을 만듭니다.
  • 현재 프로세스의 fd 전체를 닫는 cleanup 흐름을 만듭니다.
  • stdin/stdout인 fd 0과 1을 일반 파일 fd와 섞지 않도록 기준을 정합니다.
  • invalid fd가 들어와도 커널 panic이 나지 않도록 실패 흐름을 정합니다.
이 파일의 결과물: syscall.c를 다 읽은 뒤에는 "fd 등록, fd 조회, fd 닫기, fd 전체 cleanup을 어느 helper가 담당하는지"가 보여야 합니다.

syscall_init()

syscall_init()는 syscall 명령어가 들어왔을 때 커널의 어느 주소로 점프할지 CPU에 알려주는 초기화 함수입니다. 이 함수 자체는 fd table을 처리하는 곳이 아니라, syscall 입구를 준비하는 곳입니다.

읽는 포인트: B5의 핵심 로직은 이 함수보다 syscall_handler() 쪽에 가깝습니다. 다만 syscall 전체에서 공유되는 초기화가 필요한 경우 이 파일의 초기화 흐름과 연결될 수 있습니다.

syscall_handler()

syscall_handler()는 syscall 번호를 보고 어떤 작업인지 분기하는 중심 함수입니다. 현재 코드에서는 f->R.rax에서 syscall 번호를 읽고, switch로 분기합니다.

B5에서 중요한 점은 fd가 syscall 인자로 들어온다는 사실입니다. read, write, filesize, close 같은 syscall은 fd 숫자를 받은 뒤 그 숫자가 현재 프로세스의 fd table에 존재하는지 확인해야 합니다.

현재 SYS_WRITE 분기

현재 SYS_WRITE 분기는 fd, buffer, size를 레지스터에서 꺼내고, fd가 stdout일 때 콘솔 출력으로 이어지는 형태입니다. 이것은 "fd 1은 일반 파일이 아니라 stdout이라는 특수 fd"라는 사실을 보여줍니다. 

case SYS_WRITE:
{
  int fd = (int) f->R.rdi;
  char *buf = (char*) f->R.rsi;
  int size = (int) f->R.rdx;

  if (fd == STDOUT_FILENO) {
    putbuf(buf, size);
  }
  break;
}

현재 흐름을 코드 레벨로 읽기

  1. syscall_handler()에 들어오면 f->R.rax에서 syscall 번호를 읽습니다.
  2. 그 번호가 SYS_WRITE이면 case SYS_WRITE 블록으로 들어갑니다.
  3. f->R.rdi에서 첫 번째 인자인 fd를 꺼냅니다.
  4. f->R.rsi에서 두 번째 인자인 buf를 꺼냅니다.
  5. f->R.rdx에서 세 번째 인자인 size를 꺼냅니다.
  6. 그 다음 조건문은 오직 fd == STDOUT_FILENO, 즉 fd가 1인지 한 가지만 확인합니다.
  7. fd가 1이면 putbuf로 buffer 내용을 콘솔에 출력합니다.
  8. fd가 1이 아니면 아무 일도 하지 않고 break로 빠져나갑니다.
현재 상태의 한계: 이 코드는 fd 1(stdout)만 잠깐 알아봅니다. fd 2 이상의 일반 파일 fd를 저장한 적도 없고, 찾는 table도 없고, 없는 fd를 판단하는 기준도 없습니다.

현재 코드에서 아직 없는 것

  • fd가 2 이상일 때 현재 프로세스의 fd table에서 파일을 찾는 흐름이 없습니다.
  • open()으로 열린 파일을 fd table에 등록하는 흐름이 없습니다.
  • close()로 fd table에서 entry를 제거하는 흐름이 없습니다.
  • write()의 반환값을 f->R.rax에 넣는 흐름이 아직 보이지 않습니다.
  • 유저가 넘긴 buf가 안전한 주소인지 확인하는 흐름이 없습니다.
  • fd가 stdout도 아니고 일반 파일 fd도 아닐 때의 실패 정책이 없습니다.

어떻게 고쳐야 하나: 개념 레벨

고치는 방향은 SYS_WRITE 안에 조건문을 계속 덧붙이는 것이 아니라, fd를 해석하는 책임을 fd table core로 분리하는 것입니다. 현재 코드는 "fd 1이면 콘솔"이라는 한 가지 사실만 알고 있습니다. B5 이후에는 커널이 fd를 세 종류로 나누어 생각할 수 있어야 합니다.

fd 종류 의미 개념적 처리 방향
0 stdin read에서는 입력 장치, write에서는 잘못된 방향으로 본다.
1 stdout write에서는 콘솔 출력, read에서는 잘못된 방향으로 본다.
2+ 일반 파일 fd 현재 프로세스의 fd table에서 열린 파일을 찾아 파일 API로 넘긴다.

따라서 B5에서 해야 하는 핵심은 "fd 2 이상을 만났을 때 볼 수 있는 현재 프로세스의 fd table"을 만드는 것입니다. 그 table이 있어야 write가 stdout이 아닌 일반 파일 fd를 처리할 수 있고, read, filesize, close도 같은 기준으로 fd를 해석할 수 있습니다.

개념적 목표: 현재 흐름은 fd == 1만 아는 단일 특수 케이스입니다. 바뀐 흐름은 "예약 fd인지 확인하고, 일반 fd면 현재 프로세스의 fd table에서 찾는다"가 되어야 합니다.
공부 질문: stdout이 아닌 fd가 들어오면 왜 fd table lookup이라는 단계가 필요할까요? 그리고 lookup 실패가 실제 파일 API 호출로 이어지면 어떤 문제가 생길까요?

현재 SYS_EXIT 분기

현재 SYS_EXIT 분기는 종료 메시지를 출력하고 thread_exit()으로 넘어갑니다. B5-F 관점에서는 여기서 직접 fd table을 보는 것이 아니라, thread_exit() 이후 프로세스 종료 경로에서 자원 정리가 일어난다는 연결을 이해하는 것이 중요합니다.

4. process.c 읽기

process.c는 유저 프로세스의 실행, 종료, 주소 공간 정리를 담당합니다. B5에서 이 파일을 보는 이유는 "프로세스가 끝날 때 남아 있는 fd를 어디서 정리할 것인가"라는 질문 때문입니다.

process_exit()

process_exit()는 현재 프로세스가 종료될 때 호출되는 함수입니다. 현재 코드 주석도 프로세스 자원 정리를 이 근처에서 하라고 안내합니다. FD Table Core에서는 유저 프로그램이 직접 닫지 않은 fd들이 이 시점에 남아 있을 수 있다는 점이 중요합니다.

이 파일에서 해야 할 일

  • process_exit()가 진짜 프로세스 종료 흐름이라는 점을 확인합니다.
  • 종료 시 fd table에 남은 열린 파일이 있을 수 있다는 가정을 둡니다.
  • 남은 fd 전체 cleanup을 프로세스 종료 흐름과 연결합니다.
  • process_cleanup()은 주소 공간 정리이고, fd cleanup은 파일 자원 정리라는 점을 구분합니다.
  • exec 중 주소 공간 교체와 진짜 exit 종료를 섞지 않도록 흐름을 확인합니다.
  • 종료 메시지, wait/exit 상태, fd cleanup이 서로 방해하지 않는 순서를 생각합니다.
읽는 포인트: process_exit()는 "프로세스 단위 자원"을 정리하는 큰 문맥입니다. fd table도 프로세스별 자원이므로 이 함수의 흐름과 연결해서 이해해야 합니다.

process_cleanup()

process_cleanup()는 page table 같은 주소 공간 자원을 정리합니다. B5에서 중요한 구분은 fd cleanup과 주소 공간 cleanup이 같은 개념이 아니라는 점입니다. fd table은 열린 파일 자원이고, page table은 메모리 주소 변환 자원입니다.

따라서 공부할 때는 "파일 자원 정리"와 "주소 공간 정리"의 순서와 책임을 분리해서 생각해야 합니다. 이 구분을 놓치면 exit, exec, file close의 의미가 섞이기 쉽습니다.

thread_exit()와의 연결

Pintos의 흐름에서는 syscall의 exit 처리가 thread_exit()으로 넘어가고, userprog 빌드에서는 그 과정에서 process_exit()이 호출됩니다. 즉 syscall.c의 exit 분기와 process.c의 종료 정리는 한 흐름으로 이어집니다.

공부 질문: 유저 프로그램이 open()만 하고 close()를 부르지 않은 채 종료하면, 그 파일은 어느 레이어에서 정리되어야 자연스러울까요?

5. syscall.h 읽기

syscall.h는 syscall.c가 외부에 공개하는 함수 선언을 담는 헤더입니다. 현재는 syscall_init()만 선언되어 있습니다.

헤더의 역할

C에서는 한 파일에 정의된 함수를 다른 파일에서 사용하려면, 보통 헤더에 그 함수의 선언을 둡니다. 그래서 syscall.h는 "다른 파일이 syscall 관련 함수의 존재를 알 수 있게 하는 약속"입니다.

B5에서 왜 볼까?

fd table 관련 내부 함수가 syscall.c 안에서만 쓰이면 헤더에 공개할 필요가 없습니다. 하지만 프로세스 종료 흐름처럼 process.c에서 호출해야 하는 syscall 쪽 정리 함수가 생긴다면, 그 함수는 파일 경계를 넘어 보일 필요가 있습니다.

이 파일에서 해야 할 일

  • process.c에서 호출해야 하는 fd cleanup 함수가 있는지 판단합니다.
  • 그 함수가 syscall.c 안에 정의된다면, process.c가 알 수 있도록 공개 경계를 만든다고 이해합니다.
  • 외부에 공개할 함수와 syscall.c 내부에 숨길 helper를 구분합니다.
  • fd lookup, fd allocation 같은 내부 helper까지 헤더에 공개하지 않도록 주의합니다.
  • 헤더에는 최소한의 약속만 둔다는 원칙을 지킵니다.
중요한 구분: 모든 헬퍼를 헤더에 공개하는 것은 좋은 방향이 아닙니다. 헤더에는 다른 파일이 알아야 하는 최소한의 약속만 들어가는 편이 좋습니다.

세 파일의 연결 흐름

syscall.c 유저 syscall을 해석하고 fd가 필요한 요청을 fd table 사고로 연결한다.
process.c 프로세스가 끝날 때 남은 프로세스 자원을 정리하는 흐름을 가진다.
syscall.h 파일 경계를 넘어 필요한 syscall 관련 함수만 외부에 알려준다.

B5를 공부할 때는 syscall.c만 보지 말고, fd table이 프로세스별 자원이라는 점 때문에 process.c의 종료 흐름까지 같이 봐야 합니다. 그리고 두 파일 사이에 함수 호출 경계가 생기면 syscall.h가 왜 필요한지도 자연스럽게 보입니다.
