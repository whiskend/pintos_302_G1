multi-oom 테스트 쉽게 이해하기

multi-oom은 단순히 메모리가 부족해지는지만 보는 테스트가 아니다. 프로세스를 많이 만들고, 파일을 많이 열고, 일부 프로세스를 일부러 비정상 종료시키면서 커널이 자원을 끝까지 회수하는지 확인한다.

한 줄 요약

multi-oom은 fork 실패와 비정상 종료 이후에도 자원이 새지 않는지 보는 테스트다.

한 번 깊게 fork하는 것만 성공하면 부족하다. 같은 작업을 여러 번 반복해도 매번 비슷한 깊이까지 fork할 수 있어야 한다.

테스트가 하는 일

테스트 소스는 pintos/tests/userprog/no-vm/multi-oom.c에 있다. 핵심 상수는 두 개다.

상수 의미
EXPECTED_DEPTH_TO_PASS = 10 최소 10단계 이상 자식 프로세스를 만들 수 있어야 한다.
EXPECTED_REPETITIONS = 10 같은 fork 압박 테스트를 10번 반복한다.
1. 자식 프로세스를 계속 만든다. make_children()이 자식을 만들고, 그 자식이 다시 자식을 만드는 식으로 깊게 내려간다.
2. 각 프로세스는 파일을 많이 연다. consume_some_resources()는 open(test_name)을 반복해서 fd와 파일 객체를 많이 만든다. 일부러 close하지 않는다.
3. 일부 자식은 일부러 죽는다. NULL 포인터 접근, kernel 주소 접근, 잘못된 포인터로 open() 호출 같은 방식으로 비정상 종료된다.
4. 부모는 wait 결과를 확인한다. 비정상 종료한 자식은 wait() 결과가 -1이어야 한다.
5. 이 과정을 10번 반복한다. 첫 번째보다 나중 반복에서 fork 깊이가 줄어들면, 이전 반복에서 자원이 새고 있다는 뜻이다.

왜 OOM 테스트인데 open이 많이 나올까?

이 테스트는 메모리만 쓰는 게 아니라, 파일 descriptor 자원도 같이 압박한다. 

for (fd = 0; fd < 126; fd++) {
  if (open(test_name) == -1)
    break;
}

각 프로세스는 파일을 많이 열고 close하지 않은 채 종료될 수 있다. 그러면 커널은 프로세스 종료 시점에 남아 있는 fd를 전부 정리해야 한다.

즉 multi-oom은 fd cleanup 테스트이기도 하다. process_exit()에서 fd table을 비우지 않으면 반복할수록 열린 파일 객체와 fd entry가 누적될 수 있다.

테스트가 잡는 큰 문제들

문제 왜 실패하는가
fork 실패 시 중간에 할당한 자원을 안 돌려준다. 반복할수록 남은 메모리가 줄어서 fork 가능 깊이가 낮아진다.
자식이 비정상 종료했는데 부모에게 정상 종료처럼 보인다. wait(pid)가 -1을 반환해야 하는 구간에서 실패한다.
프로세스 종료 시 fd table을 정리하지 않는다. 각 프로세스가 열어 둔 파일들이 계속 남아 자원 누수가 생긴다.
잘못된 유저 포인터가 kernel panic으로 이어진다. 테스트는 일부 자식을 일부러 잘못된 주소 접근으로 죽인다. 커널 전체가 죽으면 안 된다.
thread page, page table, child status 같은 자원을 누수한다. 한 번은 통과해도 10번 반복하면서 점점 fork 깊이가 낮아진다.

정상 흐름과 실패 흐름을 나눠서 보기

정상 자식

  1. 부모가 fork()를 호출한다.
  2. 자식이 만들어진다.
  3. 자식이 파일을 많이 연다.
  4. 자식이 다시 자식을 만든다.
  5. 더 이상 fork할 수 없으면 깊이를 exit code로 부모에게 전달한다.

일부러 죽는 자식

  1. 부모가 테스트용 자식을 하나 만든다.
  2. 자식이 파일을 많이 연다.
  3. 자식이 NULL 주소나 kernel 주소에 접근한다.
  4. 커널은 해당 자식만 exit(-1)처럼 종료시킨다.
  5. 부모의 wait()는 -1을 받아야 한다.

핵심은 "실패해도 정리하고 돌아온다"이다. fork가 실패하든, 자식이 죽든, open이 실패하든, 그 과정에서 이미 잡은 자원을 놓고 나와야 한다.

반복하는 이유

메모리 누수는 한 번 실행으로는 잘 안 보일 수 있다. 그래서 multi-oom은 첫 번째 실행에서 도달한 깊이를 저장한 뒤, 같은 작업을 10번 더 한다. 

first_run_depth = make_children();

for 10 times:
  current_run_depth = make_children();
  current_run_depth가 first_run_depth보다 작으면 실패

만약 첫 번째 반복에서 자원을 조금 흘렸다면, 두 번째나 세 번째 반복부터는 더 빨리 메모리가 부족해진다. 그러면 fork 가능한 깊이가 낮아지고 테스트가 실패한다.

현재 코드에서 같이 볼 곳

파일 볼 내용
pintos/userprog/process.c process_fork(), __do_fork(), process_wait(), process_exit()
pintos/userprog/syscall.c fork, open, 잘못된 포인터 검증, sys_exit(-1) 흐름
pintos/userprog/exception.c page fault가 user process 하나의 비정상 종료로 이어지는지
pintos/threads/thread.c thread_create(), thread_exit(), dying thread page 회수
pintos/include/threads/thread.h fd_table, child/wait 관련 상태가 thread에 어떻게 들어 있는지

통과를 위한 개념 체크리스트

  • fork() 실패 시 이미 할당한 보조 구조체를 정리한다.
  • 자식 초기화 중 실패하면 부모가 실패를 알 수 있어야 한다.
  • 비정상 종료한 자식의 exit code는 부모의 wait()에서 -1로 보여야 한다.
  • 잘못된 유저 포인터 접근이 kernel panic이 아니라 해당 프로세스 종료로 끝나야 한다.
  • 프로세스 종료 시 fd table에 남은 파일을 모두 닫는다.
  • 프로세스 주소 공간과 page table을 종료 시 정리한다.
  • 부모가 wait()한 뒤 child status를 적절히 제거한다.
  • 같은 테스트를 여러 번 반복해도 fork 가능한 깊이가 줄어들지 않는다.

기대 출력

(multi-oom) begin
(multi-oom) Spawned at least 10 children.
(multi-oom) success. Program forked 10 iterations.
(multi-oom) end

.ck 파일은 user fault와 exit code 출력 일부를 무시하도록 되어 있다. 그래서 중요한 건 위 네 줄이 정상적으로 나오는지다.

한 문장으로 정리

multi-oom은 "자원이 부족한 순간"을 보는 테스트가 아니라, 자원이 부족하거나 프로세스가 비정상 종료된 뒤에도 커널이 깨끗한 상태로 돌아오는지를 보는 테스트다.
