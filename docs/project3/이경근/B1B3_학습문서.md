1. 제일 큰 그림
Project 3는 한 문장으로 이겁니다.

"프로세스가 쓰는 가상 메모리를, 실제 RAM보다 더 유연하게 관리하자."

그래서 커널은 4가지를 구분해야 합니다.

page: 프로세스 입장의 가상 메모리 한 칸
frame: 실제 RAM 한 칸
pml4: CPU가 쓰는 실제 주소 변환표
spt: 커널이 따로 들고 있는 page 설명서 모음
비유하면:

page = 책의 특정 페이지
frame = 책상을 한 칸 빌린 자리
pml4 = "이 책 페이지는 지금 어느 책상에 펼쳐져 있다"는 안내판
spt = "이 페이지는 원래 어떤 내용이고, 필요하면 어디서 가져와야 하는가"라는 기록 카드
2. page와 frame
이 둘을 제일 먼저 확실히 구분해야 합니다.

page는 가상 메모리 단위입니다.
frame은 실제 물리 메모리 단위입니다.
예를 들어 유저 프로그램이 0x8048000을 접근하면,
그 주소가 속한 가상 page가 있고,
그 page가 실제 RAM의 어떤 frame에 올라가 있으면 접근이 됩니다.

즉:

virtual page -> physical frame
중요한 점:

page는 "논리적인 메모리 칸"
frame은 "실제 메모리 칸"
3. pml4와 spt
이 둘도 많이 헷갈립니다.

pml4:

CPU가 직접 참고합니다
지금 당장 매핑된 것만 압니다
"이 가상주소는 어느 physical frame으로 가야 하나?"만 압니다
spt:

커널이 관리합니다
아직 RAM에 없는 page 정보도 압니다
"이 주소는 원래 유효한가?"
"유효하다면 나중에 어떻게 복구해야 하나?"
를 압니다
즉:

pml4 = 하드웨어 번역표
spt = 커널의 VM 장부
왜 둘 다 필요하냐?
pml4는 현재 매핑만 아는데,
Project 3에서는 아직 안 올린 lazy page도 관리해야 하기 때문입니다.

4. 왜 hash를 쓰나
SPT는 결국 이런 질문에 답해야 합니다.

이 fault 난 주소에 해당하는 page가 있나?
이걸 매번 빨리 찾아야 합니다.
그래서 va -> page lookup용으로 hash를 씁니다.

핵심:

key = pg_round_down(va)
value = struct page
왜 pg_round_down?
예를 들어 fault 주소가 0x8048123이어도,
실제로 찾고 싶은 건 그 주소가 속한 페이지 0x8048000입니다.

즉 주소 정책은 반드시:

SPT key = page boundary 주소
이걸 안 지키면 lookup이 망가집니다.

5. intrusive hash_elem
Pintos hash는 C 스타일입니다.
객체 안에 연결용 노드를 박아 넣습니다.

그래서:

struct page {
    ...
    struct hash_elem hash_elem;
};
이 의미는:
"이 page 객체 자체를 hash table 원소로 쓰겠다"입니다.

별도 spt_entry wrapper를 안 만드는 이유는:

할당이 단순해지고
lookup 결과를 바로 struct page *로 쓸 수 있기 때문입니다
즉:

struct hash는 컨테이너
struct page는 원소
hash_elem는 컨테이너에 꽂히는 고리
6. writable
writable은 아주 중요합니다.

왜 필요하냐?

page fault가 났을 때, 이게 정상적인 lazy load인지
아니면 read-only page에 write한 잘못인지
구분해야 하기 때문입니다.
예:

code page: 보통 writable = false
stack/data page: 보통 writable = true
또 claim할 때도:

pml4_set_page(..., page->writable)
로 넘겨야 해서, page 공통 필드에 두는 게 맞습니다.

7. claim이란 무엇인가
claim은 "SPT에만 있던 page를 실제로 쓸 수 있게 만드는 것"입니다.

순서:

frame 하나 확보
page <-> frame 연결
pml4에 매핑 생성
내용 채우기
즉:

설명서만 있던 page -> 실제 RAM 위에 올림
이 작업이 vm_claim_page() / vm_do_claim_page()의 본질입니다.

8. lazy loading
이게 Project 3 핵심입니다.

기존 방식:

실행 파일 로드 시 모든 page를 한 번에 메모리에 올림
lazy loading:

지금은 안 올림
대신 "나중에 이 주소를 처음 접근하면 어디서 어떻게 읽어야 하는지"만 기록
실제 첫 접근에서 page fault 발생
그때 비로소 읽어 옴
즉:

미리 적재하지 않고, 필요할 때 적재한다
왜 좋나?

안 쓰는 page는 끝까지 안 읽어도 됨
프로세스 시작이 가벼워짐
RAM을 덜 씀
9. VM_UNINIT
lazy loading을 하려면 "아직 정체가 완전히 실체화되지 않은 page"가 필요합니다.
그게 VM_UNINIT입니다.

뜻:

이 page는 유효하다
하지만 아직 frame도 없고 내용도 없다
첫 fault 때 initializer를 불러서 진짜 page로 바꾼다
즉 VM_UNINIT은 placeholder입니다.

10. initializer와 aux
lazy loading에서 제일 중요한 설계입니다.

page fault가 나중에 났을 때,
커널은 알아야 합니다:

어느 file에서 읽는가
어느 offset부터 읽는가
몇 바이트 읽는가
나머지는 얼마나 0으로 채우는가
그래서 aux가 필요합니다.

예:

struct lazy_load_arg {
    struct file *file;
    off_t ofs;
    size_t read_bytes;
    size_t zero_bytes;
};
이 aux는 말하자면
**"나중에 이 page를 만드는 레시피"**입니다.

initializer는 그 레시피를 실행하는 함수입니다.

즉:

aux = 재료/설명서
init = 조리법 실행 함수
11. load_segment가 왜 바뀌나
Project 2의 load_segment()는 바로:

palloc_get_page()
file_read()
memset()
install_page()
를 했습니다.

Project 3에서는 바뀝니다.

이제 load_segment()는:

실제로 읽지 않고
VM_UNINIT page를 만들고
aux만 채워서 SPT에 등록합니다
실제 file read는 나중에 lazy_load_segment()가 합니다.

즉:

Project 2 load_segment() = 즉시 적재
Project 3 load_segment() = 나중 적재 예약
12. stack도 VM 방식으로 바뀐다
초기 stack도 이제 VM 규칙 안으로 넣어야 합니다.

기존:

바로 page 하나 깔고 매핑
Project 3:

stack page도 page 객체로 등록
필요하면 claim
나중에는 stack growth도 같은 철학으로 처리
즉 stack도 예외가 아니라 VM의 한 구성원입니다.

13. lifetime / ownership
이건 구현할 때 꼭 생각해야 합니다.

질문:

aux는 누가 만들지?
누가 free할지?
file 포인터는 lazy load 시점까지 살아 있나?
원칙:

aux는 보통 page마다 따로 malloc
lazy_load_segment()가 끝나면 free
한 번도 fault되지 않고 종료될 수도 있으니 uninit_destroy()도 염두에 둬야 함
이걸 정하지 않으면 메모리 누수나 use-after-free가 납니다.
